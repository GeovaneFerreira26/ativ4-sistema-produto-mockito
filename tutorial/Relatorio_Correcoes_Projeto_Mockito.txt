1. DIAGNOSTICO GERAL
======================================================================

Foram analisados o PDF da atividade e os arquivos Java anexados.

O problema que explica os mocks nao serem inicializados e a ausencia do import
da classe real MockitoExtension nos dois arquivos de teste. Os arquivos possuem
@ExtendWith(MockitoExtension.class), mas nao importam:

import org.mockito.junit.jupiter.MockitoExtension;

Na arvore do projeto apresentada anteriormente aparece uma classe chamada
MockitoExtension dentro do codigo de teste. Essa classe nao deve substituir a
extensao fornecida pela dependencia mockito-junit-jupiter.

CORRECAO:
- Remover a classe MockitoExtension.java criada manualmente, caso ela exista.
- Importar org.mockito.junit.jupiter.MockitoExtension nos dois testes.
- Manter @ExtendWith(MockitoExtension.class) acima de cada classe de teste.

Sem a extensao oficial, @Mock e @InjectMocks nao sao inicializados pelo ciclo
de testes. Isso e compativel com o erro observado anteriormente:
NullPointerException ao tentar chamar ProdutoRepository.salvar(...), e testes
esperando IllegalArgumentException mas recebendo NullPointerException.

OUTROS PROBLEMAS IDENTIFICADOS:
1. ProdutoService.java nao preserva a causa da falha ao salvar: o PDF determina
   new ErroAoSalvarProdutoException("Falha ao salvar o produto", e), mas o
   arquivo atual chama o construtor com apenas uma mensagem.
2. ErroAoSalvarProdutoException.java possui somente construtor de um argumento;
   precisa aceitar mensagem e causa para corresponder ao codigo do PDF.
3. ProdutoServiceTest.java declara package projetoMockito, enquanto
   PedidoServiceTest.java declara package projetoProdutoMockito. Na estrutura
   exibida, os dois testes estao sob o pacote/projetoProdutoMockito. Padronizar
   os dois arquivos para projetoProdutoMockito.
4. PedidoService.java ainda esta na versao-base do PDF e nao trata a falha de
   PedidoRepository. O PDF apresenta esse tratamento como desafio opcional
   (Atividade 7, Cenario D). Como o projeto ja possui
   ErroAoSalvarPedidoException e o teste correspondente, o metodo deve ser
   adaptado para que esse teste passe.
5. Nao foi anexado um arquivo pom.xml nesta remessa. Portanto, nao e possivel
   confirmar a configuracao Maven real do projeto. A secao 6 deste relatorio
   apresenta apenas o trecho de dependencias que deve ser conferido com o PDF.

7. CORRECAO 5 - PedidoService.java (DESAFIO 7, CENARIO D)
======================================================================

CAMINHO:
src/main/java/sistemaProdutoMockito/pedidos/PedidoService.java

SITUACAO:
O arquivo anexado corresponde a versao-base do PDF. Nessa versao, uma falha
RuntimeException de PedidoRepository.salvar() se propaga diretamente.

Entretanto, o projeto anexado ja possui:
- ErroAoSalvarPedidoException.java
- Um teste chamado deveConverterFalhaAoSalvarPedidoNaVersaoMelhorada()

Para esse teste passar, implementar o Cenario D do desafio do PDF.

ADICIONAR O IMPORT:

import sistemaProdutoMockito.exception.ErroAoSalvarPedidoException;

No metodo criarPedido(), manter todas as validacoes e o calculo existentes.
SUBSTITUIR SOMENTE:

        pedidoRepository.salvar(pedido);

POR:

        try {
            pedidoRepository.salvar(pedido);
        } catch (RuntimeException e) {
            throw new ErroAoSalvarPedidoException(
                    "Falha ao salvar o pedido", e);
        }

O final do metodo permanece:

        return pedido;

RESULTADO:
- A quantidade invalida continua gerando IllegalArgumentException.
- Produto inexistente continua gerando ProdutoNaoEncontradoException.
- Estoque insuficiente continua gerando EstoqueInsuficienteException.
- A falha do PedidoRepository passa a gerar ErroAoSalvarPedidoException.
- Se ProdutoRepository.buscarPorId() lancar RuntimeException, o fluxo e
  interrompido antes de chamar PedidoRepository.salvar().

NOTA SOBRE OS TESTES EXISTENTES:
O teste devePropagarFalhaDoPedidoRepositoryNaVersaoBase usa
assertThrows(RuntimeException.class). ErroAoSalvarPedidoException estende
RuntimeException; portanto, essa verificacao tambem aceita a excecao especifica.
O teste deveConverterFalhaAoSalvarPedidoNaVersaoMelhorada verifica o tipo
especifico exigido pelo desafio. Os dois podem permanecer ativos.
